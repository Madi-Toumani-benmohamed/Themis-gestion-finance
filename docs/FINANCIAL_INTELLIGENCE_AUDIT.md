## Portée et méthode

Audit statique des contrats, handlers, règles SQL, composants React, migrations et tests existants. Aucune donnée bancaire réelle n’a été consultée. Les documents antérieurs (`ANALYSIS_AUDIT.md`, `ANALYSIS_IMPLEMENTATION.md`, `FINANCIAL_DATA_AUDIT.md`, `SIMULATOR_UX.md`, `TRANSACTIONS_AUDIT.md`) décrivent plusieurs lots déjà intégrés ; les constats ci-dessous ont été recoupés avec le code présent. Aucun comportement n’est déclaré validé par simple lecture de documentation.

## Architecture actuelle

Le flux d’import passe par `parser` puis `normalize.Label`, applique les alias de propriétaire, persiste le libellé brut (`transactions.label`), le nom affiché (`display_label`), la clé de regroupement (`merchant`) et le type partiel (`label_kind`). Le moteur `categorize` applique des règles déterministes sur le libellé brut. Une seconde étape `ai.AutoEnrich` stocke des propositions dans `transaction_suggestions` ; seul un PATCH explicite les applique. Les tags vivent dans `tags` et `transaction_tags`; les règles peuvent les ajouter à l’import ou lors d’une réapplication.

Les lectures d’analyse sont regroupées autour de `analysis_report.go`, `reliability.go`, `analysis_discoveries.go` et des handlers analytiques. Elles utilisent des montants exacts en centimes, des périodes bornées et une preuve de couverture documentaire. La page Analyse réutilise ces rapports, expose des sources navigables et distingue les états de chargement/erreur. Le Dashboard reste un agrégateur de widgets historiques : KPI, flux, solde, catégories, tendances, budgets, récurrences et anomalies.

La simulation utilise trois mois civils terminés ancrés sur les dernières données, exclut le mois courant et calcule en centimes/rationnels ; les scénarios restent locaux. Le Knowledge Graph est facultatif : l’import envoie des faits transactionnels de manière asynchrone et le chat peut en rechercher. Les lectures SQL de l’application restent la source financière de référence.

## Corrections P0 retenues pour ce lot

1. Reconnaître les retraits explicitement marqués `Ret Distrib`, `Ret DAB` ou `Retrait DAB` comme `label_kind=cash_withdrawal`, avec affichage stable `Retrait DAB` et sans créer de marchand dans la colonne `merchant`. Le libellé brut et chaque transaction restent inchangés ; la détection de récurrence utilisera un groupe de présentation stable.
2. Corriger le Title Case par rune pour préserver UTF‑8.
3. Retirer une heure bancaire explicitement reconnue (`14h23`, `10H21`) du nom nettoyé générique, sans altérer le brut ni les lieux/marchands voisins.
4. Encadrer par transaction la création d’alias et la propagation, faire remonter les erreurs, et limiter la normalisation de motif à la même condition de correspondance utilisée par le lecteur d’alias. Conserver le mode exact/motif lors de l’édition d’un alias. Aucune fusion floue ou suppression de transaction.

Le changement de normaliseur s’effectue via le backfill existant, versionné, qui ne touche ni montants, ni dates, ni catégories, ni empreintes. La compatibilité de lecture des anciens `label_kind` est préservée ; aucune migration n’est requise.

## Éléments à conserver et manques fonctionnels

À conserver : moteur de règles partagé, confirmation humaine des alias/suggestions IA, tags éditables par opération, rapport analytique centime exact, couverture par relevés/comptes, navigation vers sources, scénarios non persistés et KG facultatif.

Manques établis : identité marchand stable distincte du texte; provenance et exceptions des tags; validation des alias motif contre les éléments visés; rétractation des faits KG corrigés; métrique calibrée d’incertitude/non-répétition des découvertes; adoption de la couverture et du type de données par tous les widgets; distinction économique explicite entre remboursement, revenu et transfert apparié. Ces travaux dépassent le correctif P0 et ne justifient pas une refonte générale.

## Risques et vérifications

Le champ `label_kind` est textuel et déjà consommé par analyses, imports, API et UI : le nouveau type doit rester une simple classification descriptive, traité comme dépense ordinaire et jamais comme transfert. Le `merchant` vide pour une opération de type évite l’identité commerciale artificielle, mais certaines vues de marchands retomberont sur `display_label` et l’afficheront comme groupe d’opérations. La propagation d’alias reste une action utilisateur explicite ; les changements atomiques doivent être couverts par un test d’intégration PostgreSQL synthétique et vérifier l’isolation propriétaire. Aucun enregistrement validé ne sera directement modifié dans la base durant cette intervention.

Validations exécutées : `go test ./...` avec PostgreSQL 16 jetable via `THEMIS_TEST_DATABASE_URL`, `go vet ./...`, `node --test src/components/*.test.mjs` et `npm run build`. Le test d’alias simule un échec SQL de propagation et vérifie le rollback de l’alias ; l’isolation propriétaire et le backfill sont testés sur tables temporaires. Aucune suite navigateur n’est ajoutée dans ce lot de normalisation.
